# Phase 1 — ecosystem integration audit

**Date:** 2026-10-14 · **Decision:** retain the existing integration; proceed only to bounded remediation and qualification, not a universal-capability release.

## 1. Executive result

The application has a tested local-first foundation, not a qualified universal AI ecosystem. The five primary areas remain **Chat, Image, Video, Plugins, MCP**. Useful assistant weights, real image/video generation, Intel Core Ultra 5 qualification, and durable autonomous execution are not established.

This was an **audit-only increment** on `arena/fe54d09a-ragam`. All **208 pre-existing nonignored files**, including uncommitted work, retain their pre-audit SHA-256 hashes. No application code, configuration, dependencies, runtime installation, weights, or training data was changed. No commit, push, merge, new branch, or remote inference was performed. The three additions are this report, the evidence JSON, and the isolated observational probe script.

### Verified now

- `npm run verify`: **509 Core + 75 Web + 575 Fabric = 1,159 passing tests**, followed by a successful production Vite build.
- Web dependency audit: **0 known vulnerabilities reported** by `npm audit`, including development dependencies.
- Existing Python advisory checker: no installed version of its **five checked packages** covered by a known GitHub advisory. This is not a full environment or upstream supply-chain audit.
- Running Core: Strict Offline, **0 registered / 0 ready models**; generation capabilities unavailable. Production Web responds; separate Fabric responds with **5 of 8 stages runnable**. Core exposes Fabric configuration, but no Core-to-Fabric invocation path was found; running Fabric is not an integrated research loop.
- Synthetic loopback probes reproduced five limitations: unauthenticated session-list access, metadata-only readiness promotion, a body exceeding its configured provider timeout, caller-declared classification replacing detected classification, and loss of a task after application recreation.

**Release blockers:** authenticated authority, end-to-end egress containment, honest inference qualification, untrusted-code isolation, persistent task execution, and licensed/benchmarked useful models. Keep the running preview restricted to trusted development; do not attach sensitive data or expose these APIs to untrusted clients.

### Boundary ownership

- **Web → Core:** same-origin `/api`; Core owns policy, routing, catalog, sessions, Plugins and MCP. Browser fields cannot be trusted as identity or approval authority (R01–R02).
- **Core → runtime:** narrow provider operations; separate discovery, authenticated reachability, model availability, modality conformance, resource fit, and successful inference. Current operational discovery does not yet preserve all these distinctions (R04).
- **Core → Fabric:** configuration fields exist, and the standalone Fabric service implements `/status` and `/pipeline/run`, but no Core invocation path was found. Implement an explicitly versioned, authenticated bridge with data-rights checks and bounded execution before calling this integrated. `AETHERIS_FABRIC_ENABLED` is not proof of working integration; the shell's configured-URL label is not connectivity.
- **Artifacts → Klyvaron:** provenance, hashes, licence/attribution, parent base and transformations, reproducible training/evaluation, release/rollback gates. Lite/Pro/Max are product tiers, not invented resource guarantees.
- **External gateways/tools:** approved recipient, purpose, minimum data, budget and network containment. No agent can grant itself privileges. User hardware participation in company training/shared inference requires separate consent.

## 6. Recommended Phase 2 sequence and acceptance gates

1. **Authority and containment first:** resolve R01–R03/R07 before sensitive data, arbitrary extensions, or public service access. Keep trusted built-ins and explicit offline refusals. Do not turn on remote inference as a workaround.
2. **Make provider status and deadlines truthful:** resolve R04–R05 with fixture regressions, separating the catalog from inference eligibility. Keep unknown licence, capability, cost and hardware metadata unknown.
3. **Qualify one useful CPU-first Lite configuration:** after licence review and explicit installation approval, benchmark an actual supported model/runtime on the user's machine. llama.cpp is a candidate; Ollama is an alternative; choose on measured fit, not product names. Evaluate OpenVINO only where model conversion/device support and measured gains justify it. No requirement for company GPUs.
4. **Persist and recover tasks:** resolve R06 before claiming durable autonomy. Prove recovery and side-effect idempotency under restart, cancellation, worker death and retry exhaustion.
5. **Expand by measured modality and governed improvement:** real Image/Video, replaceable LiteLLM inference, licensed Klyvaron derivatives and Sparsiz experiments each need their own integration/evaluation gate. Pro/Max and industry packs follow qualified workloads, not a universal-coverage claim.

**Phase 1 is complete within the stated targeted source-audit scope.** Remediation and runtime/model qualification have not been performed. Every subsequent increment should retain these evidence boundaries, preserve the working application, pass the full suite and include a reviewable rollback path.
