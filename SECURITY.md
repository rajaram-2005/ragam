# Security Policy

## Supported Versions

| Version | Supported |
| ------- | --------- |
| 5.1.x   | ✅ Yes |
| 5.0.x   | ❌ No |
| 4.0.x   | ✅ Yes |
| < 4.0   | ❌ No |

Only versions explicitly marked as supported are eligible for security updates. Users of unsupported versions should upgrade to a supported release whenever possible.

## Reporting a Vulnerability

We take the security of this project seriously and appreciate responsible security research.

If you discover a potential security vulnerability, please report it privately so that it can be investigated and resolved before technical details are made public.

### How to Report

**Preferred method: GitHub Private Vulnerability Reporting**

1. Open this repository on GitHub.
2. Navigate to the **Security** tab.
3. Select **Report a vulnerability** under Security Advisories, if this feature is enabled.
4. Provide the details needed to reproduce and assess the issue.

**Alternative method: Email**

Send your report to **ramkpraja175@gmail.com** with the subject line:

`Security Vulnerability Report`

Do not report undisclosed vulnerabilities through public GitHub issues, discussions, pull requests, or public forums.

### Include in Your Report

Where possible, provide:

- A description of the vulnerability and its potential impact.
- The affected version, component, or configuration.
- Steps to reproduce the issue.
- Proof-of-concept code or screenshots, if applicable.
- Suggested mitigation or remediation.
- Your preferred method of contact for follow-up questions.

Do not include real credentials, private keys, personal information, or sensitive production data in your report.

### Response and Resolution Process

We aim to follow this process for every valid report:

1. **Acknowledgment:** Within 3 business days.
2. **Initial assessment:** Evaluate the report, estimate severity, and identify affected versions.
3. **Status updates:** At least every 7 calendar days while the investigation remains active.
4. **Remediation:** Develop a fix or mitigation appropriate to the severity and technical complexity.
5. **Release and disclosure:** When appropriate, publish a security advisory, release patched versions, and provide upgrade or mitigation instructions.

These are target response times, not guaranteed resolution deadlines. Complex vulnerabilities may require additional investigation.

### If a Report Is Accepted

If a vulnerability is confirmed, maintainers will work to:

- Assess its severity and scope.
- Identify affected releases and configurations.
- Develop, test, and release an appropriate fix where feasible.
- Provide remediation guidance to affected users.
- Publish relevant security information when appropriate.

### If a Report Is Declined

If a report does not identify a security vulnerability, cannot be reproduced, or falls outside the project's security scope, we will explain the decision and provide the reasoning where possible.

A declined report may be reconsidered if additional evidence or reproduction steps become available.

### Responsible Disclosure

Please allow maintainers a reasonable opportunity to investigate and address a reported vulnerability before publicly disclosing technical details.

Do not exploit vulnerabilities to access data without authorization, disrupt services, compromise other users, or cause damage. Security testing must be limited to systems and environments for which you have permission.

We appreciate responsible researchers who help improve the security and reliability of this project.

## Scope

This policy covers security vulnerabilities in the project's maintained source code, supported releases, and project-controlled components.

Issues affecting third-party dependencies or external services may also need to be reported to their respective maintainers.
